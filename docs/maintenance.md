# Maintenance notes — what to update after a re-run

## 1. The report narrative (`report/build_report.js`)
The report is prose plus tables. Tables and figures are regenerated by the pipeline (charts) or typed
into the script (tables). After each re-run, open `outputs/Facts_Summary.md` and revise:

- **Executive Summary** — headline percentages, the five root-cause paragraphs, the "what is being asked" paragraph.
- **Section 2 KPI table** — every `Current` cell.
- **Section 3.1 – 3.6** — the finding tables (rows are literal strings) and the prose paragraphs.
- **Section 7 exposure table** and **Appendix A traceability counts** (recompute the counts from each workbook's traceability sheet).

Then set `REPORT_REVISION` in `config.py`, update the revision/date lines on the cover page in the
script, and rebuild with `node report/build_report.js`. The table of contents is a Word field —
Word updates it on open.

A future improvement is to have the script read `work/facts.json` for the KPI table and the
finding tables so that only the prose needs a human. The facts file already contains every value.

## 2. Prose cells in the workbooks that carry baseline figures
These are `Read Me`, `Gap Rules` (impact / root-cause text) and traceability rows written as
literal text in the `RULES` dictionaries and `tr` lists. The counts on the same sheets are
formulas and refresh automatically; the sentences do not. Review after each run:

| Script | What to check |
|---|---|
| `src/s07_wo_build.py` | Read Me "Governing documents"; `RULES` text for G10, G11, G12, G15, G16, V01, V09, V10, V11, V13, R01, R02, H01; AM-001 Traceability rows (`tr`); permissions rows (G-6.3/6.4/6.5); Failure Codes findings list; the "Other by hours" KPI note (from MaintenanceHoursByType) |
| `src/s02_assets.py` | Read Me "Headline"; `RULES` text for A01, A08–A10, A12, A14, A15, A19; Strategy Traceability rows; Warranty sheet notes |
| `src/s04_pm_build.py` | Read Me "Headline"; `RULES` text for S01, S03–S05, S12–S15 |
| `src/s06_inventory.py` | Read Me "Headline"; `RULES` text for I02–I05, I09, I10, I12, I17; usage note (`18,384 closed work orders`) |

## 3. Things that may need re-tuning
- **Equipment vs location split** (`LOCATION_CATEGORY_PREFIXES` in config) if new asset categories appear.
- **Site codes / charge departments** (`SITE_CODES`, `SITE_DEPT`) when a site is added.
- **Placeholder list** for completion notes (`PLACEHOLDER` regex in `s01_wo_score.py`) as new low-information phrases appear.
- **Miner-specific code sets** in the failure-code review (`MINER_P/C/A` in `s07_wo_build.py`) if codes are renumbered.
- **Permissions mapping proposals** (`propose()` in `s07_wo_build.py`) once the group list is redesigned — the function will map new names to blank; fill them in.
- **Bulk-load threshold** (500 assets created in one day → `_big` in `s02_assets.py`).
- **AM-001 7.3 conforming intervals** (`CONF` set in `s04_pm_build.py`) if the author changes the frequency table (e.g. accepts 26 weeks).

## 4. Known limitations of the exports (not fixable in the pipeline)
- No PM frequency code or due date on work orders → PM compliance is a proxy (Suggested Completion).
- No rostered capacity → backlog-in-weeks is at booked pace.
- Attachments, linked documents and API permissions cannot be exported through the front end.
- 2,000-row extract cap → chunk and concatenate; keep one header row.
- Meter-based schedule triggers are not exposed by the schedule report (300 active schedules show no recurrence).

## 5. Tracking changes between runs
Keep each run's `outputs/` and `work/facts.json` in a dated folder (e.g. `runs/2026-09-28/`). Diffing two
`facts.json` files gives the movement on every measure; the Facts_Summary tables can be pasted side by side.
